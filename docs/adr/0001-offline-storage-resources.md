# Offline-first database and filesystem resources

The Storage API owns multiple databases and filesystems per `(user subject, application_id)` namespace; clients of the same application share it. No other subject or application may access or select those resources. Every file belongs to the namespace subject. We rejected cross-user grants, Unix permission bits and device-key delegation: they add an authorization layer without another principal who can use it. IdP-issued tokens bind subject, application, audience and API action limits such as read/write; these limits authorize API calls, not mesh sync. Iroh endpoints establish only transport identity. Services synchronize independently of user sign-in.

The introducing user owns a device; an approved device may store their namespace by default unless an administrator restricts it, but selection starts empty. The owner may choose which of their namespace's whole resources it stores, subject to administrator storage limits; they may always deselect. A `read`-only token cannot enroll, select, deselect or revoke. The Management API owns enrollment, revocation, ownership transfer, admin storage limits, and resource selection/deselection. A regular user needs a distinct Management API permission and a matching device-owner subject to change selection; administrator authority is separate. Before selection, Management checks kind/ID/namespace through the existing Storage API GET route with a Storage read token bound to the Management actor's subject and application. Unknown or unavailable resources fail closed, including while offline; the owner may still deselect. Management does not open filesystem catalogs. Selections are recorded as synchronized control-plane state. Concurrent selection and deselection resolve to deselection; a causally later selection may restore sync. Both peers must select the resource and check locally synchronized device approval, storage limits, selection, resource kind/ID, and namespace against the other's authenticated device ID before sync. Temporarily stale policy may allow sync until convergence. Global catalog metadata is not exposed to all mesh devices; a signed-in owner lists only resources in their subject/application namespace, and background services retain only selected-resource metadata. Administrative records remain separate. Revocation stops new sync after policy convergence but cannot erase bytes already copied. Ownership transfer clears selections and local copies before the new owner can select resources; offline devices cannot resume sync until reset. A filesystem's Full/Passthrough residency is a separate local per-path choice. Resource deletion replicates a tombstone; deselection only removes a local copy. Incompatible persisted formats fail without migration or automatic deletion.
