# Offline-first database and filesystem resources

The Storage API manages multiple databases and filesystems per owning user/application, with distinct stable IDs; `ofdb` synchronizes the resource catalog and databases, and `file-system` synchronizes filesystem policy, metadata, and content. We chose separate resource grants and explicit per-device selection over treating a trusted endpoint or application namespace as permission to receive all data. This avoids copying inaccessible folders or databases onto a device while preserving offline-first replication.

Owner-only grant edits may occur offline. Concurrent grant and revoke for the same subject and scope resolve in favor of revoke; a causally later re-grant restores access. Token exchange may use locally known policy, so remote revocation only blocks new access after policy convergence; an already-issued storage-audience token remains valid until expiry, and an established connection until close. Revocation cannot erase data previously copied by a peer.

The resource catalog is control-plane data, not a third client-issued resource type; discoverable filesystem grants are a projection of authoritative `file-system` policy, not a second source of access rights. A device must be approved and explicitly selected for each resource; receivers enforce resource ID and granted scope, including folder-limited filesystem sync. Resource deletion is a replicated tombstone; deselection only removes a device's local copy. No old-format migration or automatic deletion of incompatible persisted stores is provided.
