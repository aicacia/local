# Independent servers and unified hosting

## Goal

Ship independently deployable `idp-server`, `management-server`, and `storage-server`, plus `unified-server` for single-node hosting. Unified hosting uses the same authenticated HTTP clients as separate deployments; it does not share repositories across services.

Status: implementation in progress; authentication/API direction revised. Replication ownership work must keep a strict split: Management returns a policy decision over the requested approved endpoint pair and resource; Storage binds that decision to the actual Iroh connection at both outgoing and incoming protocol handlers. The Management request endpoint IDs are claims from the authenticated Storage service, not proof to Management of an Iroh connection. Storage must derive the local ID from its endpoint and the peer ID from `Connection::remote_id()`, never from the peer's handshake descriptor, and independently enforce admission on both sides before accepting or sending resource data. A policy response alone never authenticates a peer. IdP's legacy identity-administration `/internal/*` routes and OpenAPI entries have been removed, along with IdP's associated custom credential configuration/state. Management's application/client/consent/key/user identity facade routes and device restriction route have been removed as a breaking change because no safe standard actor-verification boundary exists. The unused legacy identity methods, generic internal request helpers, forwarding test, `InternalServiceCredential` type, API export/module, and `management-service` dependency have been deleted. Management authorization state now retains only the verified subject and canonical application ID; it no longer stores the bearer token for possible forwarding. The unreferenced `idp-model::InternalDevice` contract and export have also been deleted. Do not restore these routes without a supported standard actor-verification design. Management replication policy now uses normal bearer-token APIs; the legacy internal credential type and routes are absent from the implementation. Management selection now accepts the Storage access token as `storageAccessToken` request data and validates it through IdP introspection; the custom `x-storage-authorization` header has been removed. The route's normal `Authorization` bearer remains the Management user token. Client-credentials issuance, IdP introspection, bounded OAuth clients, approved endpoint identity lookup/listing, and Management replication policy APIs have partial implementations. The `/oauth2/token` route now accepts form-body credentials for registered `client_secret_post` clients and rejects a mismatch between the request authentication method and the client registration. A temporary-database live IdP listener test verifies client-credentials issuance, no ID/refresh token, and successful bearer-protected introspection. A cross-server listener test now provisions distinct Management→IdP and Storage→Management clients in the IdP database, issues Storage tokens through the live IdP token route, and confirms the live Management listener rejects a token lacking replication-read scope after real IdP introspection. It also confirms a read-scoped token succeeds after Management resolves an approved endpoint through IdP, using separate IdP and Management databases. The live IdP listener also issues a Storage token with `idp.device.list` and returns only its approved endpoint ID. Other listener cases still use HTTP stubs; deployment provisioning and broader live receiver authorization remain. Storage has bounded IdP and Management clients, standalone endpoint creation, and a host-injected `StoragePeerNetwork` path that exposes the borrowed `Server` for protocol registration but cannot refresh or close the host-owned endpoint. IdP exposes `device_identity_from_server`, which checks that the supplied key matches the host-owned endpoint. IdP's endpoint identity constructor is not wired into a runtime builder. Its bootstrap handler and ALPN are now available from the library without enabling CLI, so a host can construct the protocol handler from IdP runtime state. Storage now exposes `StorageReplicationRuntime::start`, which accepts a host-owned `Server`, Management client, and storage runtimes; it returns the DATA handler for host router composition and runs selection sync without binding or closing the endpoint. The standalone Storage CLI still owns endpoint creation, peer refresh, Iroh router creation, and shutdown. Unified composition must register the returned DATA handler and IdP bootstrap handler on one shared router. The normal Management selected-resource response now includes the owner subject taken from the IdP-resolved endpoint identity; Storage can use this authoritative owner value when constructing replication descriptors. Replication handler source has been moved to `storage-server/src/{data_protocol,database_protocol,storage_protocol}.rs`, and IdP no longer declares or starts the old data/database/filesystem sync handlers. The database and filesystem handlers now read selected resources through Management, use the IdP-resolved owner included in that response, compare incoming descriptors against the local endpoint's current selection, and request admission using the live Storage `Server` plus `Connection::remote_id()`. They no longer use local device/selection repositories or IdP-specific `DeviceIdentity`. Obsolete repository-backed protocol test fixtures have been replaced with focused tests that require exact Management-selected owner, application, kind, and resource matches for database/filesystem descriptors. Full API-backed protocol, authenticated-connection, spoofed endpoint, revocation, and outage tests remain; replication is not accepted. Standalone Storage CLI now registers the combined DATA protocol handler on its Storage-owned endpoint and runs database/filesystem selection sync on a ten-second interval when Management and filesystem runtime configuration are present. The replication handler/sync lifecycle is extracted into a host-injected Storage runtime. Unified can now obtain its DATA handler without Storage opening a router, but unified composition and shared peer admission are not implemented; replication remains unaccepted until API-backed protocol tests and authorization validation are complete. Management admission derives source and target IDs from the supplied live Iroh `Server` and `Connection`, rather than accepting IDs from its caller. IdP currently registers a temporary no-op DATA_ALPN handler while preserving bootstrap protocol registration. This is an allowed intermediate broken state; do not mark replication moved/working until Storage handlers use owner APIs and tests verify the actual connection identity. Storage now exposes a standalone CRUD router for databases/filesystems and wires database/filesystem storage runtimes from its own data directory. CRUD and filesystem socket authorization call IdP introspection and enforce user bearer access-token type, resource/audience match, explicit actions, and `(subject, application_id)` scope. CRUD returns `401` for invalid tokens and `503` for IdP/service failures. The filesystem socket validates through IdP at upgrade and before each storage message. Invalid/revoked/expired tokens or IdP failures close the socket; upgrade failures return `401` for invalid tokens and `503` for IdP/service failures. Focused Storage tests pass. The IdP-owned Storage CRUD routes and OpenAPI entries have now been removed; IdP still owns replication runtimes/protocol handlers pending increment 8. Storage OpenAPI documents CRUD and the WebSocket route. IdP no longer mounts or documents Storage CRUD and no longer depends directly on `storage-server`; its CLI still owns the storage runtimes used by legacy replication handlers. Storage CLI applies its configured standalone prefix to resource and socket routes. Desktop callers and unified prefix composition remain to be updated. Operational service-principal authorization, replication ownership, provisioning/cutover, unified hosting, desktop/deployment wiring, and end-to-end acceptance remain unfinished. Checkboxes below record only completed work.

## Completion criteria

- [ ] Each standalone binary exposes its complete owner-scoped service API without mounting either other server. IdP identity administration is exposed only by IdP; Management does not proxy it without an IdP-verifiable actor boundary.
- [ ] Separate deployment works with three listeners, three databases/data roots, and separately provisioned identities.
- [ ] `unified-server` mounts `/idp`, `/management`, and `/storage` on one HTTP listener.
- [ ] Unified mode uses exactly one Iroh endpoint, one persisted endpoint key, and one Iroh protocol router per host. IdP bootstrap and Storage replication share that endpoint.
- [ ] Standalone IdP and Storage create and own their own endpoints. In unified mode, neither service creates, persists, or closes an additional endpoint.
- [ ] Unified and separate deployments pass the same user, management, storage, and replication scenarios.
- [ ] No server crate depends on another server crate. Only composition hosts depend on multiple servers.
- [ ] IdP/management control-plane records are not replicated into storage or copied between service databases.
- [ ] Device clients may still synchronize their own resources; this change does not remove storage replication.
- [ ] Existing user/application/resource IDs and persisted data survive an explicit, one-off export/import cutover where preservation is required; this does not require ongoing schema-migration or backward-compatibility support.
- [ ] Desktop hosting and public discovery/client URLs use the new boundaries.
- [ ] Users and services use the same IdP-issued bearer-token validation path; permissions distinguish principals, not authentication mechanisms.
- [ ] Cross-service capabilities use owner-service normal APIs. No `/internal/*` routes, service-header authentication, shared-secret route guards, or unified-mode bypasses remain.

## Target boundaries

| Component           | Owns                                                                                                                | Calls                                                                                   |
| ------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `idp-server`        | Users, keys, OAuth applications/clients/grants/consents, device registry, identity enrollment/bootstrap             | No management/storage calls required for ordinary OAuth operations                      |
| `management-server` | Roles, permissions, assignments, selection policies, and replication policy                                         | IdP token validation/device identity APIs; Storage resource reads during user selection |
| `storage-server`    | Resource metadata/content, database/filesystem runtimes, storage sockets and replication                            | IdP validation/device APIs; management policy decisions                                 |
| `unified-server`    | Composition, config, HTTP listener, single shared Iroh endpoint/key/router, lifecycle and provisioning coordination | Same HTTP APIs as standalone deployments                                                |

Keep the canonical application registry in IdP initially: OAuth already consumes it. Management application/client administration delegates to IdP after local RBAC checks. Management stores canonical IDs, not copies of the application registry. Confirm this ownership in increment 1 before changing writes.

Shared models, services, and narrowly scoped HTTP clients may be dependencies of multiple servers. Do not move cross-service orchestration into a shared service crate to conceal server coupling.

### Authentication and API boundaries

Use the existing OAuth token endpoint and bearer authorization conventions. Implement the missing client-credentials grant for background services; do not add a separate service-token issuer or route authentication mechanism. OAuth client credentials authenticate token issuance only, never resource API calls.

Services are distinct provisioned principals with explicit audience/action permissions. User and service tokens pass the same authoritative IdP checks, including active-key and principal state. A service token cannot impersonate a user, establish endpoint ownership, approve devices, or access arbitrary resources.

Expose endpoint identity lookup through IdP's normal device API and selections/admission through Management's normal policy API. Use one capability contract for authorized callers, not duplicate Storage-only and Management-only routes. Endpoint names do not establish trust; each operation enforces principal permissions.

- [ ] Management must not proxy IdP identity administration. Keep those operations on IdP's normal user-authenticated API. Revisit a Management facade only if a supported standard mechanism lets IdP independently verify the user actor, audience, permission, and audit identity; do not use forwarded actor headers, blanket service authority, or a custom delegation protocol.

Authoritative token validation/introspection is an IdP capability, not another authentication system. Receiving services authenticate their IdP requests with ordinary service access tokens and submit the token being checked as data under the chosen normal contract. IdP validates the calling service token locally, so introspection never recursively calls itself or Management. Token issuance and IdP OAuth remain usable without Management or Storage.

### Unified transport

| Destination | Separate example              | Unified example                     |
| ----------- | ----------------------------- | ----------------------------------- |
| IdP         | `https://identity.example/`   | `http://127.0.0.1:3000/idp/`        |
| Management  | `https://management.example/` | `http://127.0.0.1:3000/management/` |
| Storage     | `https://storage.example/`    | `http://127.0.0.1:3000/storage/`    |

These are internal transport URLs, not public issuers or token audiences. Standalone prefixes are configurable; unified prefixes are fixed. Join relative paths without discarding the configured prefix. Use the listener's actual bound address for unified clients, including ephemeral ports in tests. Loopback requests remain authenticated. Require TLS for non-loopback service transport.

Unified mode still has distinct service engines/data directories and distinct OAuth service principals. Do not add a second, in-process authorization implementation.

### Iroh endpoint ownership — required

**Unified mode MUST use exactly one Iroh endpoint per host.** `unified-server` owns its persisted key, endpoint, protocol router, transport-level peer admission, and shutdown. It passes the same endpoint/server handle to IdP and Storage runtime builders. IdP supplies its bootstrap handlers; Storage supplies its database/filesystem replication handlers. Register all handlers on one protocol router. Sharing only a key between two independently bound endpoints does not meet this requirement.

| Deployment         | Endpoint creation and key ownership              | Protocol registration and shutdown                                               |
| ------------------ | ------------------------------------------------ | -------------------------------------------------------------------------------- |
| Standalone IdP     | IdP CLI owns its endpoint and persisted key      | IdP host owns its router and shutdown                                            |
| Standalone Storage | Storage CLI owns its endpoint and persisted key  | Storage host owns its router and shutdown                                        |
| Unified            | Unified host owns one endpoint and persisted key | Unified host registers IdP and Storage handlers on one router and closes it once |

In unified mode, IdP and Storage must not call their standalone endpoint constructors, open a second endpoint key store, create separate protocol routers, or close the injected endpoint. IdP now has `device_identity_from_server`, and Storage has a `network`-feature `StoragePeerNetwork::from_host_server` constructor. These are only injection seams: IdP CLI still binds its own endpoint, Storage CLI still opens its standalone endpoint, and Storage's injected path deliberately cannot refresh shared admission or close the endpoint. Split and expose service runtime/protocol initialization before unified wiring.

Shared transport does not merge service state or permissions. IdP retains bootstrap ownership; Storage retains resource and replication ownership. HTTP calls still use the normal authenticated IdP/Management APIs. The shared endpoint ID does not replace distinct OAuth principals or grant resource access. Unified transport admission must support bootstrap and replication without letting a Storage refresh failure erase IdP bootstrap admission; each protocol still enforces its own authorization.

## Execution rules

Implement in order unless a dependency is explicitly noted. Numbered increments organize the work; they do not require independently mergeable or passing intermediate states.

For every increment:

- Breaking API, configuration, internal-interface, and persisted-schema changes are allowed. Do not maintain backward compatibility for old database layouts.
- Do not add incremental schema migrations as part of this plan. Update the current initial schema definition instead. For existing data, use a deliberate one-off export/import cutover only when required; otherwise require a clean reinitialization. Do not add runtime schema detection, migration chains, or compatibility wrappers.
- The repo may temporarily fail to compile or pass tests while boundaries and callers are being rewritten. Record unfinished wiring and failures, then continue through dependent increments; do not stop solely because an intermediate state is broken.
- Add/update focused tests and run targeted checks when the affected code is runnable. Record passes, failures, and deferred checks honestly; do not mark unverified acceptance criteria as passed.
- Preserve user changes. Rewrite/delete obsolete ownership and update callers without adding legacy API/database compatibility wrappers.
- Phase gates describe eventual acceptance criteria, not mandatory stop points. Revisit deferred gates during final acceptance.
- Run `cargo hack test --feature-powerset --workspace --all-targets` and `just crap` only after all implementation steps and the end-to-end harness are complete, as final validation. Do not run either per phase, per step, or for the baseline.
- Keep implementation out of `lib.rs`/`mod.rs`; keep dependencies explicit and minimal.
- Reassess complexity/risk before implementation. Security, state ownership, and data cutover are high risk; packaging/composition wiring is lower risk.
