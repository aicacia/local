# Storage split: cross-repository roadmap

## Target boundary

The storage API manages two distinct resource models: a **database** backed by `ofdb` (SQL-like tables and KV), and a **filesystem** backed by `offs/file-system` (paths, metadata and bytes). Each `(user subject, application_id)` namespace may own multiple of each, with distinct stable IDs and optional non-unique display names. An application OAuth client exchanges its user's access token for a normal storage-audience IdP access token to manage resources. There are no cross-user grants or folder scopes: a device owned by that user explicitly selects whole resources to synchronize, subject to administrator limits. `ofdb` and `file-system` own their respective data, persistence and sync. A Passthrough filesystem is read-only, does not retain file bytes locally, but still syncs metadata and obtains content from selected Full peers. `ofnet/iroh-chain` owns authenticated transport and generic ALPN routing, not resource-specific protocols. IdP token issuance is separate from storage resource management.

| Concern                                                       | Owner              | Present evidence                                                                           |
| ------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------ |
| SQL rows, schema, indexes, transactional replication          | `ofdb`             | `ofdb/crates/engine/src/kernel.rs`, `ofdb/crates/sync/src/session.rs`                      |
| KV generations and snapshots                                  | `ofdb` primitives  | `ofdb/crates/kv/src/store.rs`, `ofdb/crates/kv-sync/src/session.rs`                        |
| Filesystem paths, content, metadata, residency, file sessions | `offs/file-system` | `offs/crates/file-system/src/file_system.rs`, `src/sync.rs`                                |
| Endpoint identity, allowlist, pairing, mesh, direct streams   | `ofnet/iroh-chain` | `ofnet/crates/iroh-chain/src/server.rs`                                                    |
| Resource APIs, token validation and application/user scope    | `of` storage API   | `of/crates/storage-service/src/scoped_file_system.rs`, `of/crates/idp-service/src/oauth2/` |

Database and filesystem CRUD expose multiple IDs within each `(subject, application_id)` namespace. DB and filesystem synchronization, Management policy admission and control-plane join have focused implementations and tests. Full cross-repository regression and end-to-end resource gates remain open. The generic filesystem transport cutover is complete. The IdP/Management database holds control-plane records and is never an application database.

## Settled decisions and remaining design work

1. The storage API owns two resource models in the `(subject, application_id)` namespace: multiple DBs and filesystems with separate IDs, optional non-unique names and create/open/list/delete APIs. A client exchanges its user token for a normal storage-audience access token with subject, application, audience and API action limits; tokens do not authorize mesh sync. Only the owning subject can access a resource; there are no cross-user grants, file permission bits or folder scopes. `ofdb://<path>` is a file-backed database URI (`ofdb/src/uri.rs`), not a filesystem ID. Active `VaultId` uses have been removed.
2. Endpoints only carry traffic. `ofdb` syncs databases and the separate IdP/management control-plane database; `file-system` syncs filesystem metadata and content. The Storage API owns resource catalog identity, namespace, names and deletion status. A signed-in owner discovers resources in their namespace; background services retain only selected-resource metadata, not a global catalog. Management owns synchronized device approval, administrator limits and whole-resource selection policy. Both peers check approved endpoint identity, both selections, admin allowance, resource kind/ID and namespace before exchanging resource data. No resource is selected by default. Filesystem Full/Passthrough residency is device-local. Owner deletion replicates a tombstone, while deselection removes only a local copy.
3. `iroh-chain` owns authenticated transport and generic ALPN routing, not database/filesystem ALPNs or payload protocols. DB and FS use its generic data stream; service-specific framing, validation, bounds and sync live with `ofdb` and `file-system`, respectively. Mesh notifications are not a durable replication channel. Pairing alone never authorizes sync.
4. Database recovery and filesystem metadata/content recovery belong to `ofdb` and `file-system`, respectively. Remove old-format migration/handling code; incompatible persisted stores fail clearly and require operator removal. Never erase stored data automatically on startup.
5. Keep sibling checkouts under `aicacia/{of,ofdb,offs,ofnet}/` for now. `offs/crates/file-system/Cargo.toml` may continue to use relative paths into `ofdb`; test the documented layout. Do not introduce publishing/version migration work.

## Execution order and gates

1. **Specify the APIs.** [RESOURCE-API.md](storage/RESOURCE-API.md) and [SECURITY-TRANSPORT.md](storage/SECURITY-TRANSPORT.md) are the active contracts. R1 records Storage CRUD and Management selection/restriction routes, token boundaries and owner-only namespace. R2's two-sided admission, frame authorization and policy-convergence scenarios have focused tests. `ofdb/CONTEXT.md`, `ofdb/docs/design.md` and `ofdb/docs/goal.md` describe state units/manifests and incremental sync, not persisted envelopes/frontiers. `offs/CONTEXT.md` describes stable file IDs and KV metadata. Do not implement superseded designs.
2. **Verify sibling builds.** Document the required checkout layout and run tests from each repo using the existing path dependencies. Remove old-format migration/legacy-specific recovery; ensure incompatible stores fail clearly without deleting data. No publication changes are needed now.
3. **Implement the database path** using [01-database-plan.md](01-database-plan.md). Keep control-plane DB replication distinct from any new application database service. Gate on authenticated join, incremental sync, restart and unauthorized-scope tests.
4. **Implement the filesystem path** using [02-filesystem-plan.md](02-filesystem-plan.md). Gate on matching ID/namespace metadata and content transfer, residency, reconnect and unauthorized-peer tests.
5. **Cut over and delete stale paths** using [03-of-integration-cleanup.md](03-of-integration-cleanup.md). Do not add compatibility wrappers for unpublished legacy APIs. Gate on actual runtime builds and end-to-end resource provisioning for both kinds.

The confirmed trade-offs and revocation limits are recorded in [ADR 0001](adr/0001-offline-storage-resources.md). Historical [filesystem ADR](storage/ARD01.md) remains intact; its local-only ACL and single-namespace assumptions are superseded by ADR 0001.

## Validation and risk

Run focused crate tests first, then `cargo hack test --feature-powerset --all-targets`, format/Clippy checks and `just crap` in each affected workspace. Add end-to-end tests that issue multiple databases and filesystems for one user/application, deny cross-kind and cross-namespace access, replicate each selected resource independently, then deselect one without affecting the others. Check that an offline/restarted peer reconciles both kinds and that revocation blocks new sync after policy convergence. Verify actual runtime builds rather than assuming missing sibling dependencies have been resolved.

This is a breaking cutover plan, not a claim that provisioning, protocols or join are complete. Database issuance and SQL/KV synchronization have partial implementation and focused tests; the remaining acceptance gates are open. There is no legacy on-disk data migration.
