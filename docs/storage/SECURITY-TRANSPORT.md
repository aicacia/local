# Security and transport authorization contract

[ADR 0001](../adr/0001-offline-storage-resources.md) records the trade-offs. This document specifies the R2 authorization contract. Focused DB and filesystem tests exercise both production handlers; full cross-workspace regression remains open.

## Settled

- A resource is isolated to `(IdP token subject, application_id)`, never `client_id`. Multiple clients of one application share that user's resources. No other subject or application can open or select them. The subject owns all files in that namespace. There are no file mode bits, Unix ACLs, groups, per-file owner changes or cross-user grants.
- Users authenticate to the Storage API through sign-in or token exchange. Storage-audience tokens bind the subject, application, audience and allowed API actions such as `read` or `write`. `read`-only tokens cannot enroll, select, deselect or revoke devices/resources. Device enrollment, removal, transfer, administrator storage limits, and resource selection/deselection are Management API operations, not Storage API operations. A regular user needs a distinct Management API permission to manage selection on their own device, plus a device-owner subject match; administrator authority is separate. Storage API `read` or `write` alone cannot configure a device. Each request checks its action; token limits do not govern service-to-service sync. The service synchronizes independently of live user sessions or tokens. Iroh endpoint keys establish transport identity, not user identity or grant authority. No delegated device keys, certificates or endpoint-signed permission events.
- Every device has a persisted owner subject. Enrollment assigns the authenticated subject; pairing inherits the approving device's owner. Records without an owner are invalid and fail closed; do not infer owners or silently migrate records. Device selection is whole-resource and least-privileged by default. An approved user-owned device permits its owner's namespace by default unless an administrator restricts it; selection still defaults to none. An administrator sets limits on what a device may store; a user who introduces and owns a device selects resources in their own subject/application namespaces and may always deselect local data. An administrator cannot force retention. Filesystem Full/Passthrough remains a local per-path residency choice.
- Selection is a Management API control-plane record keyed by device ID, application ID, resource kind and resource ID, then synchronized to services. Selection starts empty; each accepted PUT selects one whole resource. Management validates `(kind, ID, application_id)` through the existing kind-specific Storage GET route using a validated Storage read token bound independently to the Management actor's subject and application. It does not open a database or filesystem catalog. The distinct Management permission and device-owner check are also required. Unknown IDs, identity mismatch or unavailable Storage APIs fail closed for selection; the owner may deselect without Storage. Enrollment assigns the authenticated owner; pairing inherits the approved accepting device's owner. Missing owners fail closed; only an administrator may transfer ownership. Before any resource frame is sent or applied, each peer independently checks its locally synchronized view: authenticated remote endpoint matches an approved device; both devices select the same resource; neither is admin-restricted; kind, ID, owner subject and application namespace match. Peer-supplied selection claims are never authoritative. Pairing/allowlisting alone does not authorize sync. Admin restriction wins over concurrent selection. Concurrent select/deselect resolves to deselected; a selection causally after the deselection may restore it. Once revocation/restriction converges, peers reject new sync; copied bytes cannot be recalled.
- Whole-resource selection of an owner's filesystem may replicate all its metadata and content: there is no other subject or per-file permission for filtering. Passthrough devices do not retain file bytes. Transfer clears selections and local copies before a new device owner can select resources; an offline device cannot resume sync until transfer/reset completes.
- Peers with temporarily stale control-plane state may continue sync until an admin restriction or device revocation converges. They then refuse new sync; copied data cannot be recalled. When the owner signs in, the API lists only resources in their `(subject, application_id)` namespace; a background service retains only selected resource metadata, not a namespace-wide catalog. Admin-only control-plane records remain separate.
- `ofnet` owns authenticated Iroh transport and generic ALPN routing; it does not define DB/FS ALPNs or payload protocols. `ofdb` owns database data, persistence and sync, including the separate IdP/Management control-plane DB. `file-system` owns filesystem resources, persistence and sync. `of` owns resource catalogs, token/Management authorization, namespace isolation and runtime wiring; it adapts transport to owning-crate sync APIs without adding another sync, framing, conflict-resolution or recovery layer. The unused `ofdb/src/resource.rs` catalog is not selection authority. Device selection is control-plane state, not a user API session.

## Owning-crate wire limits

- DB sync messages are capped at 1 MiB (`ofdb::sync::MAX_MESSAGE_BYTES`). The Iroh transport uses a length prefix and rejects oversized lengths before allocating frame payloads. Session batches default to 64 units; this does not cap sync duration or concurrency.
- Filesystem metadata-sync frames are capped at 8 MiB (`file-system::MAX_FILESYSTEM_SYNC_FRAME_SIZE`). File-session requests/responses have the same encoded-frame cap; reads are limited to 16 MiB and served in chunks. These are protocol limits, not resource authorization.
- The owning crate validates version, framing and payload before applying data. `ofnet` only routes authenticated generic streams. Admission must happen before invoking either sync API and must be rechecked before applying incoming resource state; never compensate for missing authorization with a permissive transport adapter.

## Verification status

- Background services receive only selected-resource metadata; the global Storage catalog is not replicated.
- Both peers check authorization before the first resource frame and before apply, including reconnect. Unavailable/conflicted policy fails closed; stale but not-yet-converged replicas may permit sync only within the documented convergence window.
- Focused tests cover first selection, paired-but-unselected peers, per-resource deselection, concurrent select/deselect and later reselection, reconnect after restriction/revocation, cross-kind and cross-namespace denial, and malformed/oversized frames. Broader workspace and runtime regression remains on the roadmap.
- Contract verified against `RESOURCE-API.md`, database plan D3, filesystem plan F3 and current route/policy implementations. DB admission is registered on both inbound and outbound paths; its Iroh test covers selected sync, wrong kind/namespace, admin restriction, malformed handshake, interrupted frames, reconnect and converged deselection. FS admission is registered inbound and outbound, checks policy on each transport frame, and projects only validated selected IDs. Focused tests cover both callback directions, and an integrated FS test exercises Management policy through the registered protocol handlers, including paired-but-unselected, wrong kind/namespace, live-session deselection and fresh-session recovery. Two-replica Management tests verify stale policy may admit only before revocation convergence, then denies after sync; concurrent deselect-wins and later selection are also tested. Owning-crate frame limits and transport tests pass.

The earlier proposals for cross-user grants, scoped per-file transfer to another user's device, Unix permission bits, certificate delegation and signed grant events are withdrawn. Do not implement them as prerequisites to R2.
