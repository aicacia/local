# `of` integration and deletion plan

This is a breaking cutover. No compatibility wrappers or old-data migration. Incompatible stores fail clearly; operators remove them manually. Implement namespace-scoped database resource catalog, authorization and API/runtime wiring in `of`, database data/sync in `ofdb`, filesystem resources/data/sync in `offs/file-system`, and endpoint transport in `ofnet`. `of` calls the owning crates; it does not add another replication, conflict-resolution, framing or recovery layer. Remove the unused `ofdb/src/resource.rs` catalog.

## Work order

1. Finalize the resource contract in [RESOURCE-API.md](storage/RESOURCE-API.md) and security/transport checks in [SECURITY-TRANSPORT.md](storage/SECURITY-TRANSPORT.md). Those files are the source of truth; this checklist must not reintroduce cross-user grants, file permission bits, device keys as principals, or user-session mesh sync.
2. Persist an owner subject for every device: use the authenticated enrolling subject, and inherit the approving device's owner on pairing. Records missing an owner are invalid and fail closed; do not infer owners or migrate records. Implement Management API device lifecycle, resource selection and admin storage limits; synchronize only validated selection/control-plane data to sync-owning services. Regular user requires the dedicated Management permission and owns the device; `read`/`write` Storage API credentials cannot configure devices. Persist Management selection and admin policy in the separate `ofdb` control-plane database, not in client-issued application databases; delete the standalone selection event/version model. Validate owner, Management permission and admin allowance, then check kind/ID/namespace via the existing Storage API GET route using a Storage read token verified and bound to the same subject/application before committing a selection; Storage token access alone never authorizes Management writes. An unavailable lookup fails closed for selection, but the owner may still deselect. Management does not directly open filesystem catalogs. Select/deselect must use durable `ofdb` writes and project only validated selections to sync-owning services. Verified `ofdb`'s current Automerge path with `cargo test -p engine-automerge --test kernel concurrent_same_column_updates_expose_null_and_explicit_resolution_converges` and `cargo test -p ofdb --features 'sync sql automerge redb in-memory' --test cluster_sync concurrent_inserts_offline`: distinct offline writes converge; concurrent same-column writes converge to Automerge's winner but remain reported as a row conflict, and writes fail until explicit resolution. This does not establish deselect-wins automatically. `ofdb::Engine::row_conflict_values` now exposes the competing values, and `resolve_row` provides durable conflict resolution; Management still needs to choose `NULL` whenever a deselect is among concurrent selection values and verify that through the replicated control-plane path. Keep sync admission fail-closed for conflicted policy until then; do not add a second event/version/merge layer in `of`. Both peers must have selected the same resource and pass device approval, admin allowance, kind/ID and namespace checks before sync. Concurrent deselect wins; a later selection may restore it.
3. Implement multiple DB and FS resources using [01-database-plan.md](01-database-plan.md) and [02-filesystem-plan.md](02-filesystem-plan.md). Keep each resource inside `(subject, application_id)`. Do not mix the IdP/Management control-plane DB with client-issued application DBs.
4. Replace obsolete runtime/session/network paths only after replacement tests pass. Remove missing `offs/crates/iroh-chain*` dependencies; use `ofnet` transport with minimal adapters for the owning crates' existing sync APIs. Rename `VaultId` to Filesystem ID. Delete obsolete code rather than wrapping old unpublished APIs.
5. Fix desktop/server installation join on actual `ofdb` sync APIs. Only report setup complete after durable authorized bootstrap. Keep local secret/key material out of replicated resources.
6. Delete stale docs/contracts/tests and run the full cross-repo regression gate. Preserve historical ADRs but clearly mark superseded assumptions.

## Acceptance checks

- Storage API CRUD and token action enforcement respect `(subject, application_id)`; same-application clients share resources, other subjects/apps do not. Management owns device enrollment/removal/transfer and selection; selection data is validated and no global resource catalog is sent to every device.
- Approved peers sync only resources selected on both sides, subject to admin restriction and matching resource kind/ID/namespace. Iroh endpoint identity is transport-only. Stale offline state may permit sync until policy convergence; after convergence it blocks new sync. No promise of erasing copied offline data.
- DB and FS create, restart, sync and delete independently. FS Full/Passthrough semantics remain correct. Deselect removes a device-local copy; resource deletion is a tombstone.
- Desktop join, server runtime, and workspace builds use existing APIs and compile. No missing sibling path dependencies, stale session endpoints, or unsupported checkpoint/envelope imports remain.
- No compatibility migration. Unsupported stores fail safely without automatic data deletion.

## Handoff checklist

Dependencies: resource/security contracts in [roadmap R1–R2](00-storage-split-roadmap.md#handoff-checklist), database D2–D5, filesystem F2–F5. Assign non-overlapping crates to agents; shared `ofnet` changes have one owner.

Ensure same-app OAuth clients share one user's resources; other subjects/apps and cross-kind IDs fail closed. Test create/list/open/delete, action denial, duplicate names and namespace isolation.
- [ ] **C2 — Management device policy (`of`):** Every device has a persisted owner subject. Enrollment uses the authenticated subject, including first-device approval; pairing inherits the approved accepting device's owner. Carry ownership through device models, `DeviceRepo`, persistence, replication and approval; reject records with no owner rather than inferring or migrating an owner. Keep enrollment, approval, revocation, transfer, admin storage limits, and whole-resource selection/deselection in Management API. Require a dedicated Management permission plus device-owner subject match for user selection. Admin can restrict but not force retention; approved devices allow their owner's namespace by default and start with no resources selected. Validate kind/ID/namespace through the existing Storage API GET route with a Storage read token independently bound to the authorized actor's subject/application; unknown or unavailable entries fail closed for selection, including offline. Deselect does not require Storage availability. Management does not open filesystem catalogs. Store policy in the separate `ofdb` control-plane DB; use its persistence, transactions and sync instead of a Management-owned event/version merge model. Verified current Automerge behavior: same-column concurrent writes are surfaced as row conflicts and subsequent writes fail until explicit resolution; it does not guarantee deselect-wins or expose that policy to `of`. Keep sync admission fail-closed for conflicted selection state until the owning `ofdb` path enforces deselect-wins (or the contract changes). Test owner persistence/restart/pairing, rejection of owner-missing records, least privilege, selected IDs, concurrent deselect-wins/later reselect, admin restriction, transfer clearing and revoked devices. **Progress:** owner subject is now required on `Device`, `DeviceRepo::create`, the replica row/schema and global-identity device columns. Enrollment passes validated `claims.sub`; pairing copies only a non-empty owner from an approved accepting device. Bootstrap device creation follows creation/lookup of the actual admin user. Missing-owner JSON records fail closed. The obsolete management filesystem repositories were deleted rather than shimmed against removed `file-system` APIs. **Remaining:** end-to-end verified Management selection/deselection and admin restrictions, runtime build, policy projection and two-sided sync admission. IdP device list/rename/revoke restrict by authenticated owner subject. Management now exposes PUT/DELETE `/devices/{device_id}/selection` with separate Management `devices.select` authorization and an IdP Storage-read token in `X-Storage-Authorization` for PUT. The restriction has a focused restart/selection-denial test and a signed-token mounted-route test covering permission, Storage-audience and device-state denial. The mounted test exposed and fixed an obsolete `applications.revoked_at` projection in Management permission lookup. A local `DbSelectionPolicyRepo::peers_selected_for_sync` check now reads the replicated device and selection rows and requires two distinct approved devices, matching owner/application/kind/ID, admin allowance and conflict-free policy. Focused tests cover pending/revoked/unknown peers, deselection, restriction, namespace/resource mismatch and a replicated concurrent selection conflict. Bootstrap helper IDs now use `idp_model::model::Id`; `cargo check -p bootstrap-service` and `cargo test -p bootstrap-service` pass.
