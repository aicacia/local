# Security and transport authorization: design in progress

[ADR 0001](../adr/0001-offline-storage-resources.md) records the current boundary. This is the R2 design gate, not an implemented protocol.

## Settled

- A resource is isolated to `(IdP token subject, application_id)`, never `client_id`. Multiple clients of one application share that user's resources. No other subject or application can open or select them. The subject owns all files in that namespace. There are no file mode bits, Unix ACLs, groups, per-file owner changes or cross-user grants.
- Users authenticate to the Storage API through sign-in or token exchange. Storage-audience tokens bind the subject, application, audience and allowed API actions such as `read` or `write`. `read`-only tokens cannot enroll, select, deselect or revoke devices/resources. Device enrollment, removal, transfer, administrator storage limits, and resource selection/deselection are Management API operations, not Storage API operations. A regular user needs a distinct Management API permission to manage selection on their own device, plus a device-owner subject match; administrator authority is separate. Storage API `read` or `write` alone cannot configure a device. Each request checks its action; token limits do not govern service-to-service sync. The service synchronizes independently of live user sessions or tokens. Iroh endpoint keys establish transport identity, not user identity or grant authority. No delegated device keys, certificates or endpoint-signed permission events.
- Every device has a persisted owner subject. Enrollment assigns the authenticated subject; pairing inherits the approving device's owner. Records without an owner are invalid and fail closed; do not infer owners or silently migrate records. Device selection is whole-resource and least-privileged by default. An approved user-owned device permits its owner's namespace by default unless an administrator restricts it; selection still defaults to none. An administrator sets limits on what a device may store; a user who introduces and owns a device selects resources in their own subject/application namespaces and may always deselect local data. An administrator cannot force retention. Filesystem Full/Passthrough remains a local per-path residency choice.
- Selection is a Management API control-plane record keyed by device ID and synchronized to services. Management validates `(kind, resource ID)` with the Storage API's existing kind-specific GET route before selecting; it does not open the database or filesystem catalog directly. The lookup uses a validated Storage read token bound to the Management actor's subject and requested `application_id`, in addition to the distinct Management permission and device-owner check. Unknown IDs, mismatched identity or unavailable Storage APIs fail closed for selection, even offline; the owner may still deselect without a lookup. Device enrollment, approval, revocation and ownership transfer belong to the Management API. Approval requires the already recorded owner subject; only an administrator can transfer ownership. Both peers must have selected the resource. Before exchanging resource frames, sender and receiver each check locally synchronized approval, effective admin allowance, selection, resource kind/ID, and matching namespace against the other's authenticated device ID. A request from the peer is not proof of selection. Pairing alone cannot authorize sync. An admin restriction defeats a concurrent selection. Concurrent owner select/deselect resolves to deselect; an owner selection that observes the deselection can restore sync. After revocation converges, peers reject new sync with the revoked device; previously copied bytes cannot be recalled.
- Whole-resource selection of an owner's filesystem may replicate all its metadata and content: there is no other subject or per-file permission for filtering. Passthrough devices do not retain file bytes. Transfer clears selections and local copies before a new device owner can select resources; an offline device cannot resume sync until transfer/reset completes.
- Peers with temporarily stale control-plane state may continue sync until an admin restriction or device revocation converges. They then refuse new sync; copied data cannot be recalled. When the owner signs in, the API lists only resources in their `(subject, application_id)` namespace; a background service retains only selected resource metadata, not a namespace-wide catalog. Admin-only control-plane records remain separate.
- `ofnet` owns authenticated Iroh transport and generic ALPN routing (pairing and application data only; mesh has a private internal ALPN). It must not define database/filesystem ALPNs or choose their payload protocols. `ofdb` owns database data, persistence and sync (including the separate IdP/Management control-plane database); `file-system` owns filesystem resources, data, persistence and sync. `of` owns the namespace-scoped database resource catalog, token validation, Management authorization, namespace isolation and runtime wiring. It invokes the owning crates' sync APIs through minimal transport adapters, not another sync, conflict-resolution, framing or recovery layer. The unused `ofdb/src/resource.rs` catalog is not an authority for resource selection. Device selection is a storage decision, not a user API session.

## Implementation checks

- Validate selections through the existing kind-specific Storage GET routes using a Storage read token whose subject and application are independently bound to the authorized Management actor/request. Never trust a caller-supplied ID or another subject's successful lookup. Reject unavailable Storage APIs and unknown resources; allow owner deselection without a lookup. Do not open filesystem catalogs in Management or introduce another sync layer.
- Project only selected-resource metadata to background services. Verify both sides' selection and approval at each new sync connection, before sending or applying frames.
- Test first selection, reconnect after an offline administrator restriction, concurrent select/deselect, device ownership transfer/reset, and no cross-namespace or cross-kind data transfer.

The earlier proposals for cross-user grants, scoped per-file transfer to another user's device, Unix permission bits, certificate delegation and signed grant events are withdrawn. Do not implement them as prerequisites to R2.
