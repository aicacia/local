# Storage split: cross-repository roadmap

## Target boundary

The storage API manages two distinct resource models: a **database** backed by `ofdb` (SQL-like tables and KV), and a **filesystem** backed by `offs/file-system` (paths, metadata and bytes). Each user/application may own multiple of each, with distinct stable IDs and optional non-unique display names. An application OAuth client exchanges its user's access token for a normal storage-audience IdP access token to manage resources. `ofdb` and `file-system` own their respective data, persistence and sync. Durable resource data synchronizes to authorized participating devices within their granted scope; a Passthrough filesystem is read-only, does not retain file bytes locally, but still syncs authorized metadata and obtains content from Full peers. Iroh mesh owns ALPNs and transport; endpoints know nothing about either resource model. IdP token issuance is separate from storage resource management.

| Concern                                                       | Owner              | Present evidence                                                                           |
| ------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------ |
| SQL rows, schema, indexes, transactional replication          | `ofdb`             | `ofdb/crates/engine/src/kernel.rs`, `ofdb/crates/sync/src/session.rs`                      |
| KV generations and snapshots                                  | `ofdb` primitives  | `ofdb/crates/kv/src/store.rs`, `ofdb/crates/kv-sync/src/session.rs`                        |
| Filesystem paths, content, metadata, residency, file sessions | `offs/file-system` | `offs/crates/file-system/src/file_system.rs`, `src/sync.rs`                                |
| Endpoint identity, allowlist, pairing, mesh, direct streams   | `ofnet/iroh-chain` | `ofnet/crates/iroh-chain/src/server.rs`                                                    |
| Resource APIs, token validation and application/user scope    | `of` storage API   | `of/crates/storage-service/src/scoped_file_system.rs`, `of/crates/idp-service/src/oauth2/` |

Today the database and filesystem engines are separate, but provisioning is filesystem-oriented: `ScopedFileSystemRuntime` maps `(user_sub, application_id)` to `vaults/`, and no corresponding application database provisioning contract was identified. Treat the new database resource as new work, not an alias for the IdP's existing `ofdb` database. The IdP/management database holds control-plane records; application databases need an explicit owner and scope.

## Settled decisions and remaining design work

1. The storage API owns two resource models; the owner is the user subject within an application. Implement multiple DBs and filesystems per owner with separate IDs, optional non-unique names and create/open/list/delete APIs. A client exchanges its user token via RFC 8693 for a normal storage-audience access token; only the owner edits grants. Whole-DB grants and folder-subtree FS grants are separate. `ofdb://<path>` is a file-backed database URI (`ofdb/src/uri.rs`), not a filesystem ID. Rename the misleading `VaultId` to Filesystem ID at cutover.
2. Endpoints only carry traffic. `ofdb` syncs its databases and the Storage API's resource catalog (IDs, owner, names, discoverable grant projections, deletion status); `file-system` syncs authoritative FS grants, authorized metadata and content. The catalog's FS grant projection must never become an independent permission authority. Selectable owned or granted resources are discoverable without downloading content. An approved device must explicitly select each accessible resource; a receiver checks endpoint approval, resource ID and granted scope. FS grantees receive only granted subtrees plus minimal ancestor metadata, never siblings; DB grantees receive the whole DB. Passthrough FS is read-only; residency and selection are device-local. Owner deletion replicates a tombstone, while deselection removes only a local copy.
3. `iroh-chain` owns ALPN registration/routing and transport. DB and FS use it as a library; service-specific framing, validation, and sync live with the owning crates, not endpoint handlers. Agree on distinct DB and FS protocols and frame bounds; mesh notifications are not a durable replication channel. Pairing alone never authorizes sync.
4. Database recovery and filesystem metadata/content recovery belong to `ofdb` and `file-system`, respectively. Remove old-format migration/handling code; incompatible persisted stores fail clearly and require operator removal. Never erase stored data automatically on startup.
5. Keep sibling checkouts under `aicacia/{of,ofdb,offs,ofnet}/` for now. `offs/crates/file-system/Cargo.toml` may continue to use relative paths into `ofdb`; test the documented layout. Do not introduce publishing/version migration work.

## Execution order and gates

1. **Specify the APIs.** Write down both resource IDs, create/open/list/delete, exchanged token claims, device selection, per-resource peer authorization, wire protocols and incompatible-store rejection; update conflicting descriptions in `of/CONTEXT.md`, `ofdb/docs/design.md` and `ofdb/docs/goal.md` when the implementation contract is verified. `ofdb/CONTEXT.md` describes state units/manifests, while `ofdb/docs/design.md` still claims persisted envelopes/frontiers. `offs/CONTEXT.md` describes stable file IDs and KV metadata, while `of/CONTEXT.md` still claims hash-backed content and per-folder Automerge documents. Do not implement either older description by accident.
2. **Verify sibling builds.** Document the required checkout layout and run tests from each repo using the existing path dependencies. Remove old-format migration/legacy-specific recovery; ensure incompatible stores fail clearly without deleting data. No publication changes are needed now.
3. **Implement the database path** using [01-database-plan.md](01-database-plan.md). Keep control-plane DB replication distinct from any new application database service. Gate on authenticated join, incremental sync, restart and unauthorized-scope tests.
4. **Implement the filesystem path** using [02-filesystem-plan.md](02-filesystem-plan.md). Gate on scoped metadata and content transfer, residency, reconnect and unauthorized-scope tests.
5. **Cut over and delete stale paths** using [03-of-integration-cleanup.md](03-of-integration-cleanup.md). Do not add compatibility wrappers for unpublished legacy APIs. Gate on actual runtime builds and end-to-end resource provisioning for both kinds.

The confirmed trade-offs and revocation limits are recorded in [ADR 0001](adr/0001-offline-storage-resources.md). Historical [filesystem ADR](storage/ARD01.md) remains intact; its local-only ACL and single-namespace assumptions are superseded by ADR 0001.

## Validation and risk

Run focused crate tests first, then `cargo hack test --feature-powerset --all-targets`, format/Clippy checks and `just crap` in each affected workspace. Add end-to-end tests that issue one database and one filesystem for the same user/application, deny cross-kind access, replicate each independently, then revoke one without granting access to the other. Check that an offline/restarted peer reconciles both. Existing `of` manifests reference missing `offs/crates/iroh-chain*` packages; expect integration build failures until those paths are replaced, not papered over.

This is a breaking cutover plan, not a claim that the protocols or application database issuance already exist. It provides no legacy on-disk data migration.

## Handoff checklist

Work top to bottom. Assign one checkbox to one agent; do not start dependent implementation before its contract is recorded. Each agent should update its checkbox only after its verification runs and report any blocked item with the failing command or unresolved decision.

- [ ] **R1 — Storage API contract (`of`):** Specify create/open/list/delete for multiple DBs and FSs per owning user/application, opaque distinct IDs, optional duplicate display names and an example of both kinds. Define RFC 8693 exchange of an application-client user token into a normal storage-audience access token with subject, application, resource ID, kind, read/write action and FS path scope where applicable; define owner-only grant edits, authorized resource discovery and per-device selection/deselection. KV and the catalog are not separately issued resource kinds. Done when [01](01-database-plan.md) and [02](02-filesystem-plan.md) can implement without further product-model decisions.
- [ ] **R2 — Security/transport contract (`of`, `ofdb`, `offs`, `ofnet`):** Specify offline owner-only grant operations with causal re-grant and concurrent revoke-wins for each subject/scope; do not store ACLs as a single mutable KV generation (divergent snapshots are rejected). Define local-policy token issuance, expiry/reconnect revocation windows, and peer checks for approved endpoint + selected resource + granted scope. Prevent unauthorized FS subtree metadata/content transfer. Register distinct ALPNs in `iroh-chain`; DB and FS own framing, bounds and incoming-session checks. Test stale-policy issuance, grant/revoke reconciliation, cross-kind rejection and paired-but-unauthorized peers. Depends on R1.
- [ ] **R3 — Sibling-checkout gate (`ofdb`, `offs`):** Verify `aicacia/{of,ofdb,offs,ofnet}/` sibling layout and run builds with current path dependencies. Delete legacy-format migration/recovery paths; verify incompatible `metadata.redb` fails clearly without automatic erase and document manual removal. No registry publication work. Can run alongside R1–R2.
- [ ] **R4 — Parallel implementation:** Delegate [database tasks](01-database-plan.md#handoff-checklist) to an `ofdb` owner and [filesystem tasks](02-filesystem-plan.md#handoff-checklist) to an `offs` owner. Assign one `ofnet` owner for ALPN/routing changes in `ofnet/crates/iroh-chain/src/server.rs`. Depends on R1–R2; sibling-build work may run alongside.
- [ ] **R5 — `of` cutover:** Execute [integration and deletion tasks](03-of-integration-cleanup.md#handoff-checklist) after both paths have working tests. Do not remove a live caller before its replacement is exercised.
- [ ] **R6 — End-to-end gate (`of`):** Test one user/application with multiple issued DBs and FSs: each provisions, authorizes, syncs and restarts independently; a FS grant cannot read/write/sync the DB; an unselected or revoked resource cannot start new API access/sync once local policy catches up. Test folder-limited peer sync, independent deselection versus deletion and tombstone recovery. Run each affected repo's focused tests, then feature-powerset tests and Clippy. Done when results and any pre-existing failures are recorded in this checklist or the handoff report.
