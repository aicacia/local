# `of` integration and deletion plan

This is a breaking cutover. No compatibility wrappers or old-data migration. Incompatible stores fail clearly; operators remove them manually. `of` owns resource catalogs, API authorization and runtime wiring; `ofdb` owns database data/sync; `offs/file-system` owns filesystem resources/data/sync; `ofnet` owns authenticated generic transport. Do not add another replication, framing, conflict-resolution or recovery layer.

## Work order

1. Finalize the active contracts in [RESOURCE-API.md](storage/RESOURCE-API.md) and [SECURITY-TRANSPORT.md](storage/SECURITY-TRANSPORT.md). Do not reintroduce cross-user grants, file permission bits, device keys as principals, or user-session mesh sync.
2. Management owns device enrollment, ownership, approval, revocation, admin limits and per-device whole-resource selection. Persist policy in the separate `ofdb` control-plane DB. A selection requires the owner's Management permission and a Storage read token bound to the same subject/application; validate kind, ID and namespace using the existing Storage GET route. Deselect does not require Storage availability. Both peers check locally synchronized approval, both selections, admin allowance, kind/ID and namespace before exchanging resource data. Concurrent deselect wins; causally later selection may restore sync. Keep admission fail-closed for unavailable/conflicted policy.
3. Implement multiple independent DB and FS resources within `(subject, application_id)` using [01-database-plan.md](01-database-plan.md) and [02-filesystem-plan.md](02-filesystem-plan.md). Keep control-plane data separate from application resources.
4. Replace obsolete runtime/session/network paths only after replacement tests pass. Use `ofnet` generic data streams and owning-crate protocols; remove stale paths instead of adding compatibility wrappers.
5. Join the control-plane device over an authenticated Iroh bidirectional stream using `ofdb` sync. HTTPS may authorize/register the joining device but must not carry device-to-device sync. Bind bootstrap admission to the registered endpoint and report setup complete only after successful durable synchronization.
6. Delete stale current docs/contracts/tests and run the cross-repository regression gate. Preserve historical ADRs but mark superseded assumptions.

## Acceptance checks

- Storage API CRUD and token action enforcement respect `(subject, application_id)`; same-application clients share resources, other subjects/apps do not. Management owns device lifecycle and selection; no global catalog is sent to every device.
- Approved peers sync only resources selected on both sides, subject to admin restriction and matching kind/ID/namespace. Stale offline state may permit sync until policy convergence; copied offline data cannot be recalled.
- DB and FS create, restart, sync and delete independently. Full/Passthrough semantics remain correct. Deselect removes a device-local copy; resource deletion is a tombstone.
- Desktop join, server runtime and workspace builds use supported APIs. No missing sibling dependencies, stale session endpoints or unsupported checkpoint/envelope imports remain.
- No compatibility migration. Unsupported stores fail safely without automatic data deletion.
