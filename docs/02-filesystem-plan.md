# Filesystem resource and transport plan

## Boundary and current state

`offs/crates/file-system` owns paths, metadata (`metadata.redb`), content (`.data/`), persistence, sync, file sessions and residency. `of` supplies namespace/token checks, resource mapping and Management policy; it calls the filesystem API rather than implementing another filesystem sync, conflict-resolution, framing or recovery layer. Metadata uses KV snapshots; `Transport` and `FileSessionService` are current seams. The `of` runtime currently provisions by `(user_sub, application_id)`; replace the implicit one-filesystem namespace with multiple stable Filesystem IDs and remove `VaultId` naming. Each file belongs to the namespace subject. No mode bits, groups, ACLs, cross-user grants, folder scopes, or row-database metadata replication.

Storage resources are isolated by `(subject, application_id)`; OAuth clients in one application share a namespace. Storage API tokens govern API `read`/`write`, not mesh sync. Management owns device lifecycle, admin storage limits and whole-resource selection. A filesystem syncs only when both approved peers selected the same Filesystem ID and locally allow it. Passthrough remains read-only and stores no content bytes. `ofnet/iroh-chain` owns ALPN and transport; `file-system` owns protocol framing, bounds, metadata/content sync and recovery. See [SECURITY-TRANSPORT.md](storage/SECURITY-TRANSPORT.md).

## Acceptance checks

- A user/application can create/open/list/delete multiple filesystems, independently of databases, with stable Filesystem IDs, duplicate optional names, restart and replicated deletion tombstones. A second OAuth client of that application shares the namespace; other subject/application and Database IDs cannot access it. Storage API `read`/`write` bounds are enforced.
- Both selected peers exchange filesystem metadata and content only for the matching Filesystem ID/namespace. Unselected, wrong-ID/kind/namespace, revoked-after-convergence and admin-restricted peers fail closed. Paired-only peers cannot sync. Enforce bounds and protocol versions before applying incoming data.
- Full peers store bytes; Passthrough peers store metadata only, fetch from selected Full peers, and cannot write. Test no Full provider, stale revisions, interrupted/cancelled reads, reconnect, lag recovery, tombstones, and unsupported metadata schema failure without data deletion.
- Deselection removes that device's local copy only. Resource deletion propagates a tombstone. No legacy migration or automatic deletion.
