# Storage resource API contract

The Storage API manages databases and filesystems; the Management API owns device enrollment, approval, revocation, ownership transfer, administrator restrictions, and per-device resource selection. Database and filesystem data/sync remain owned by `ofdb` and `file-system`. See [SECURITY-TRANSPORT.md](SECURITY-TRANSPORT.md) for peer authorization. Storage CRUD and Management selection routes are implemented. DB and filesystem sync handlers enforce local peer policy on inbound and outbound paths; broader workspace and end-to-end regression gates remain tracked in the roadmap.

## Identity and tokens

A resource is isolated to `(IdP token subject, application_id)`; `application_id` is derived from the validated OAuth client, not supplied by the request. Multiple clients of one application share that subject's resources. Other subjects and applications cannot discover, open or select them. Each namespace may own multiple databases and filesystems, each with its own stable, kind-specific opaque ID and optional non-unique display name. Names are labels, not identifiers, and need not be unique. For example, one application can create databases `{ id: db_a, name: "main" }` and `{ id: db_b, name: "main" }` plus a filesystem `{ id: fs_a, name: "main" }`; the IDs are independent and a filesystem ID is never a database ID. No file mode bits, groups, cross-user grants or per-folder access rules exist.

Clients use IdP-issued storage-audience access tokens from sign-in or token exchange. Tokens bind subject, application, audience and allowed API actions such as `read` and `write`; the Storage API checks the action and resource namespace on each request. A read-only credential cannot create or delete resources or change device configuration. No access token authorizes mesh sync: services sync selected resources independently of live user sessions.

## Storage resource routes

| Operation         | Route                                            | Result                                                |
| ----------------- | ------------------------------------------------ | ----------------------------------------------------- |
| Create database   | `POST /storage/databases` with optional `name`   | `201` new Database ID in caller's namespace           |
| List databases    | `GET /storage/databases`                         | caller's `(subject, application_id)` databases only   |
| Open database     | `GET /storage/databases/{database_id}`           | metadata if ID and namespace match                    |
| Delete database   | `DELETE /storage/databases/{database_id}`        | tombstone catalog entry for caller-owned database     |
| Create filesystem | `POST /storage/filesystems` with optional `name` | `201` new Filesystem ID in caller's namespace         |
| List filesystems  | `GET /storage/filesystems`                       | caller's `(subject, application_id)` filesystems only |
| Open filesystem   | `GET /storage/filesystems/{filesystem_id}`       | metadata if ID and namespace match                    |
| Delete filesystem | `DELETE /storage/filesystems/{filesystem_id}`    | tombstone catalog entry for caller-owned filesystem   |

Read/list/get require the `read` storage action. Create/delete require `write`. The API derives `application_id` from the validated OAuth client and `subject` from validated token claims; callers cannot choose either namespace component. A kind-specific ID never authorizes the other kind. Unknown, deleted, or wrong-namespace IDs fail closed. Delete returns `204` and tombstones the catalog entry, blocking subsequent gets and opens; it does not revoke already-issued in-process handles or itself remove offline device copies. Resource deletion and device deselection are distinct: deletion is a resource tombstone; deselection removes only that device's local copy. A Passthrough filesystem is read-only and stores no local file bytes.

## Management API boundary

The Management API enrolls/revokes/transfers device ownership and configures storage selection/administrator limits. Every device has a persisted owner: enrollment uses the authenticated subject, and pairing inherits the approved accepting device's owner. Records missing an owner fail closed; no owner is inferred or migrated. Selection is whole-resource, defaults to none, and is stored as synchronized control-plane policy keyed by device ID and resource kind/ID. An approved user-owned device may store its owner's namespace by default unless an administrator restricts it; selection still defaults to none. A device owner may choose resources from their own subject/application namespaces subject to admin limits; a read-only credential cannot mutate selection. Concurrent deselection beats selection; a subsequent deliberate selection can restore sync. Transfer clears selections and local copies before a new owner may select.

A signed-in owner lists their own resources to choose selections. Background services retain only selected-resource metadata, not a namespace-wide catalog. Management routes are mounted under `/management` in the collocated IdP service; the standalone Management router uses the same paths without that prefix:

| Operation                        | Route                                                                                    | Authorization and effect                                                                                                                                                                   |
| -------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Select one resource              | `PUT /management/devices/{device_id}/selection`                                          | Requires Management `devices.select`, an approved device owned by the actor, and `X-Storage-Authorization: Bearer <storage-read-token>`. Body: `{ "applicationId": "…", "kind": "database" | "filesystem", "id": "…" }`. Management validates the token subject, audience/actions, owner, application and the resource via the corresponding Storage `GET`; writes one whole-resource selection; returns `204`.    |
| Deselect all resources on device | `DELETE /management/devices/{device_id}/selection`                                       | Requires Management `devices.select` and matching persisted owner; needs no Storage service/token; returns `204`.                                                                          |
| Deselect one resource            | `DELETE /management/devices/{device_id}/selection/{application_id}/{kind}/{resource_id}` | Requires Management `devices.select` and matching persisted owner; needs no Storage service/token; returns `204`.                                                                          |
| Set administrator restriction    | `PUT /management/devices/{device_id}/restriction`                                        | Requires Management `devices.restrict` and an approved device. Body: `{ "adminAllowed": true                                                                                               | false }`; returns `204`. This endpoint requires the authoritative shared IdP/Management device repository in the collocated deployment; standalone Management fails closed when it cannot establish device ownership. |

Selection defaults to none. `adminAllowed: false` blocks selection and sync; administrators cannot force retention. A regular user cannot use Storage `read` or `write` permissions to change device policy. A successful Storage lookup with a different subject/client is not authorization to select. Unknown resources, invalid token/namespace binding, and unavailable Storage APIs fail closed for selection, including while offline. Deselect remains available without Storage. Neither Storage nor Management tokens are persisted or used for mesh sync. There are no Storage API device routes.

Both peers check locally synchronized device approval, admin allowance, selection, resource kind/ID and matching namespace against the authenticated peer before sending or applying resource data. Filesystem transport rechecks authorization on each frame. Stale policy can allow sync until it converges; after convergence revocation/restriction blocks new sync, but cannot recall copied data. Focused protocol tests cover DB and filesystem admission; the broader regression gate remains open.
