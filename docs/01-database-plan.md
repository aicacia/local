# Database resource and replication plan

## Boundary and current state

`of` owns namespace-scoped resource identity, issuance, catalog metadata and authorization, and invokes `ofdb` for data access and sync. It must not implement a second database sync, conflict-resolution, framing or recovery layer. `ofdb` owns SQL-like rows, KV data, persistence and sync. `ofdb/crates/sync/src/{protocol,session,transport}.rs` implements manifest/state-unit and incremental SQL sync over `SyncTransport`; `ofdb/crates/kv-sync/src/session.rs` separately handles KV. Neither is a user-authorization service. `of/crates/db/src/native.rs` opens the IdP/management control-plane database; that database must not be exposed as a client-issued application database.

The target is multiple independent Database IDs in each `(subject, application_id)` namespace, shared by that application's OAuth clients but invisible to other subjects and applications. The Storage API uses IdP-issued storage-audience tokens with `read`/`write` action bounds for [resource CRUD](storage/RESOURCE-API.md). Management owns device enrollment, whole-resource selection and admin limits. [SECURITY-TRANSPORT.md](storage/SECURITY-TRANSPORT.md) defines admission. No cross-user grants, per-row permissions, token-gated mesh sessions or file-system ACLs.

`ofnet/iroh-chain` exposes generic pairing/data transport; database sync framing and any subprotocol identifiers belong to `ofdb`, not `ofnet`. A selected database syncs independently of live user sessions. Both peers must check approved device identity, locally synchronized selection, admin restriction, kind/ID and namespace before sending or applying database state. Sync the whole database, not a subset; a stale policy may permit sync only until convergence. Protect framing with explicit size/version bounds. Mesh notifications are not durable delivery.

## Acceptance checks

- One user/application creates multiple databases without creating a filesystem; distinct IDs work across restart and duplicate optional names do not affect identity. Another subject/application and a filesystem ID cannot list/open/delete them. `read` cannot create/delete; `write` and verified namespace are required.
- Two approved devices selected for the same database exchange durable SQL-like and KV data through the DB protocol. Unselected, revoked-after-convergence, wrong-kind/ID/namespace and admin-restricted devices exchange no DB state. A receiving peer also rejects unauthorized or oversized/malformed frames before apply. Retry/restart and interrupted imports converge without mesh delivery guarantees.
- Control-plane IdP/management DB join uses the supported `ofdb` sync contract over an Iroh bidirectional stream. HTTPS may be used between the joining device and the IdP/control plane to authenticate and register setup, but never for device-to-device synchronization. Do not route bootstrap through application-database selection or filesystem sync. Setup must authorize the Iroh peer specifically for bootstrap (bound to its registered endpoint identity); do not broadly allow pending peers or treat pairing/allowlisting alone as authorization. Setup is not complete before committed bootstrap; failure/restart retries safely.
